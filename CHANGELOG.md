# Changelog

The format of this file is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and versioning follows [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Changed

- **Breaking: macOS 15 or later and WebKitGTK 2.50 or later are required.** yagura now supports only the system releases their vendors still update. The macOS app does not open on macOS 14 or earlier, and the `.deb` depends on `libwebkit2gtk-4.1-0 (>= 2.50)`. See [Install](README.md#install).
- **Breaking: nothing is typed into a window's input any more.** `send_message`, a `send_handoff` to an existing window, chat posts and the daemon's notices are put in the window's inbox as envelopes, and the CLI takes them through its own doors: its hooks, its wake command, or the request it is started with. GitHub Copilot CLI, Muse Code and Grok Build, which the daemon used to type into while they waited for input, now take what waits at their next turn, after a tool call, or in one block when their turn stops (`deliver = "block"`), which makes the CLI go on with it. See [`docs/mcp-setup.md`](docs/mcp-setup.md#how-the-daemon-delivers-text).
- **Breaking: `send_message` and `send_handoff` answer with `id`, `state` and `note`.** `state` is `delivered` (the CLI was handed the envelope), `queued` (it waits in the inbox; `note` says when it is handed over and what could lose it) or `undelivered_no_delivery`; `send_handoff`'s `delivery` field, and its `taken` and `undelivered_timeout` values, are gone. The call waits only while a wait the CLI left registered, or its wake command, carries the envelope, never for the window's next turn. Each envelope carries its `id` as the first key of its JSON (`[yagura message] {"id":...}`, `[yagura handoff] {"id":...}`, and the chat envelope), and a CLI can be handed the same envelope twice: act once per `id`. `read_chat`'s delivery states read `queued` and `delivered` (they were `pending` and `taken`), and a queued entry carries `note`. See [`docs/mcp-setup.md`](docs/mcp-setup.md#send_message).
- **The GUI shows what waits and how a post stands.** A window whose inbox holds messages shows an envelope mark with their number on its sidebar row and in its header (nothing is shown at 0, or when the daemon does not report the count). The Chat panel labels a post's delivery **Queued** or **Delivered**. Settings > Approvals has seven switches, one fewer: `send_keys` is gone. Settings > Integrations reads **Registered with different arguments** when a registration's `args` differ.
- **A door says it printed what it was handed only once its output is written.** An envelope counts as delivered then; one a door was carrying when its CLI cut it off, or when the daemon ended, waits in the inbox again and is handed over again.
- **`send_message` keeps the line endings of its `text` as written, and takes several lines.** It used to turn every LF and CRLF into a lone CR, so that a console line editor would submit the line it typed, and refused a line break anywhere else; the text now reaches the window inside an envelope, where a line ending is data. It is refused as `invalid_argument` when it is longer than one answer of the window's doors carries.
- **Breaking: `interrupt_window` follows the window profile's new `[interrupt]` table and answers with an `outcome`** (`interrupted`, `stop_requested`, `stop_requested_unconfirmed`, `no_open_turn`) next to `window_id`. The user's own interrupt (the GUI's, or any approver's) writes the profile's keys for the user. An AI's interrupt stops Claude Code, Grok Build and Muse Code at their next tool call through their hooks instead of by a keystroke, and GitHub Copilot CLI at the tool calls it plans after the interrupt (the calls of a batch it already planned are not stopped), so a draft in the input line survives it, and Codex CLI refuses it with the new `interrupt_unsupported` error. `[limits] interrupt_bytes` now applies only to a window whose profile declares no `[interrupt]`, and to one opened without a profile. See [`docs/mcp-setup.md`](docs/mcp-setup.md#interrupt_window).
- **When an AI interrupts a window, what that window was waiting for ends at once**: its `wait_for_status` answers `outcome: "stop_requested"`, and its requests awaiting an approver are withdrawn with the new `requester_interrupted` error (the approval dialog closes for that reason). While its marked turn is open, a request it starts ends the same way at once. The user's own interrupt ends none of these.
- **A bridge declares the profile it speaks for, and a window opened from a launch profile that gives its CLI hooks takes a bridge as itself only when it declares the window's own profile.** The bundled bridges are started, and registered, with `--profile <id>`; a bridge that declares another profile, or none, is refused (`profile_mismatch`) and stays `External`. In the same windows a `--hook` door that names another profile's id does nothing. A plain shell window, and one opened from a raw command, accept them as before. See [`docs/mcp-setup.md`](docs/mcp-setup.md#requester-identification).
- **Breaking: a launch that names a profile yagura does not list is refused as `profile_not_found`.** `open_window` with `profile`, `send_handoff` with `profile` and `open_task_window`, over MCP and IPC, answered `invalid_argument` for it, the code of an argument to correct, so a caller could not tell that the profile is not there and that it has to pick another. Not listed is any profile `list_profiles` does not report: one whose file is gone or fails to load, an id of the wrong form, or one with no command for this operating system. A disabled profile is still refused as `profile_disabled`, and a plan or a task assignment that names an unknown profile, and the GUI's profile editing, still answer `invalid_argument`. See [`docs/mcp-setup.md`](docs/mcp-setup.md#error-handling).
- **A subagent's hook is told apart once per profile, and what it does is one rule for every profile.** The new top-level `subagent_pointer` replaces each event's `skip_if`. A subagent's hook reports `running` and `waiting_approval` for the window -- a background subagent that is working shows the window `running` -- and nothing else: no other status, no session, no delivery, and no start or end of the window's turn. `--skip-if` follows the same rule, so `--emit-status running --skip-if <pointer>` (and `waiting_approval`) now reports for a subagent too. The bundled Claude Code, Codex CLI, GitHub Copilot CLI and Grok Build profiles name the pointer. See [`profiles/README.md`](profiles/README.md#hook-events).
- **The bundled Claude Code profiles call `--hook` for every status event**, as the other bundled profiles do, and give Claude Code a wake file to watch (see Added).
- **`[delivery] max_chars` is now `max_bytes`, counted in bytes of the answer as the door prints it** (JSON escapes and the room's introduction included, and for a wake command the arguments that carry the text). `max_chars` is read as that many bytes, with a warning. A text that no answer of the window's forms could carry is refused when it is sent, and the room's introduction, which a context answer carries too, makes the largest text a window takes that much smaller. See [`profiles/README.md`](profiles/README.md#delivery).
- **One sender may leave at most 8 envelopes waiting in one window** (`[limits] max_queued_per_sender`); one more is `resource_exhausted`. Every caller that is no window shares one such bound. When a window ends, the envelopes it left waiting in other windows are taken out.
- **The limits on unanswered handoffs (4) and on pending approvals are counted per caller: one MCP session across all of its tool calls, or one direct IPC connection.** They used to be counted per daemon connection, and `yagura-mcp` opens one for each call, so an MCP session's calls were never counted together. The refusal now reads `too many handoffs are in flight (per-caller limit)` (it read `per-connection limit`). The limit on pending waits is still per connection. See [`docs/mcp-setup.md`](docs/mcp-setup.md#send_handoff).
- **The bundled Muse Code profile on macOS and Linux passes its server and hooks at every launch, as `wsl-muse-code` does, and registers nothing**, so it has no Muse Code row in Settings > Integrations there. On Windows it is registered as before.
- **The bundled Grok Build profiles hand Grok Build a launch overlay in `GROK_CONFIG`**, which keeps the window's credentials out of the shells Grok Build's tools run, while every setting of yours stays in effect. Until a window's overlay is made, its credentials do not speak for it (`launch_overlay_pending`). See [`profiles/README.md`](profiles/README.md#launch-overlay).
- **The bundled GitHub Copilot CLI profiles call `--hook` for every event**, take the inbox after each tool call, and hand it over as a block at `agentStop`.
- **The session store records more of a window**: whether its launch overlay was made, where its wake file is, and the times its CLI gives its hooks (migrations 023 to 025), so a window the daemon takes back after a restart keeps them.
- **A window's doors are told the times its CLI was given when the window opened.** The daemon reads them from the `[hook_timeout]` table of the profile the window was opened from, once, at the open; editing or removing the table later changes what the next window is told, not an open one. A door given no time -- a window opened from no profile, or a table with no key for the door and no `default` -- prints what it was handed without measuring (it used to take 10 seconds). See [`profiles/README.md`](profiles/README.md#hook-timeout).
- **The bundled Claude Code profiles record Claude Code's own hook times (600 seconds, and 30 for `UserPromptSubmit`), and the bundled GitHub Copilot CLI profiles record Copilot's (30 seconds)**, which apply because their hooks register none.
- **A window open asked for once the daemon has begun to end every window is refused with `invalid_state`** ("the daemon is shutting down"). An open already past its checks is waited for, and its window is ended with the others.
- **The minimum supported Rust version is now 1.89** (it was 1.88), which `rusqlite` 0.41 requires. See [`docs/building.md`](docs/building.md).
- **`get_window_status`'s `last_output_summary` is now the last 500 characters the window's screen shows**, its wrapped rows joined as `read_output` joins them, rather than the last 500 characters of `read_output`'s text: rows that scrolled off the top are no longer part of it. The daemon answers it from what it holds, so a window whose terminal does not answer no longer holds up its status. See [`docs/mcp-setup.md`](docs/mcp-setup.md#get_window_status).
- **Four default keys change on Windows and Linux, and two on macOS**, so that they no longer take keys the CLIs in your windows use. Windows and Linux: next window `Ctrl+Tab` is now `Ctrl+Shift+f`, previous window `Ctrl+Shift+Tab` is now `Ctrl+Shift+b`, settings `Ctrl+,` is now `Ctrl+Shift+s`, next window needing you `Ctrl+Shift+a` is now `Ctrl+Shift+j`. macOS: next window `Ctrl+Tab` is now `Shift+Meta+]`, previous window `Ctrl+Shift+Tab` is now `Shift+Meta+[`. To get the earlier keys back, set them in Settings > Keyboard or in `keymap.toml`. See [`docs/keymap.md`](docs/keymap.md#default-keys).
- **The IPC protocol is now revision 34.** New are the request `run_hook`, which the `--hook` door sends, and the answer `hook_input_wanted`, which asks the door for the few values of the hook's input an event reads; `door_read` and `deliver_printed`, which replace a door's reads (`deliver_context`, `deliver_take`, `deliver_wait` and `run_hook`'s read) so that what a door takes stays the daemon's until the door says it printed it, while the earlier reads are answered with nothing to print; `withdraw_message` with `message_withdrawn`; `queued_count` in `WindowInfo` and `window_status`, and `queued_ids` in `window_status`; `status_boot` in `WindowInfo` and `status_changed`; `build_launch_overlay` with `launch_overlay`; an optional `declaration` (`{"profile": "<id>"}`) in `identify` and in the relay's `relay_hello`, whose contract version stays 1; `outcome` in `window_interrupted`; the reason `requester_interrupted` in `approval_withdrawn`; and `id`, `state` and `note` in `text_sent` and `handoff_sent`. `send_keys` and `keys_sent` are gone. A `pong` comes only once the daemon has fed a window every byte of output it had received before the `ping`, so a client can wait on it; the frames themselves are unchanged.
- **In the `yagura-daemon` library API, `control::close_window` returns `Closed`**, whose `exit` is `Ok(ExitConfirmed)` once the window reports `exited`, or `Err(ExitUnobserved)` when its holder had not reported the exit within the grace. Only the daemon can make an `ExitConfirmed`.
- **After updating, out-of-date hook entries are written again for you.** The hooks the bundled Grok Build, Muse Code (`muse-code` on Windows) and Codex CLI profiles leave in a CLI's own settings, or in its trust record, run `yagura-daemon --hook <profile-id> <Event>`: they name only the profile and the event, and what the event does is read from that profile each time the hook runs, so a release that changes it rarely changes the entry. When the entries a registration wrote no longer match -- those of 0.3.0 and earlier among them -- the daemon writes the current ones itself, when a window opens and when Settings > Integrations lists the rows, and logs one line saying so. It does this only while the instance is still registered there, judged by what that instance's Remove would take out: the registration's own hooks entry (Muse Code), the hooks in the registration's own file (Grok Build), or the `[mcp_servers.<name>]` table (Codex CLI). It writes only the entries the registration owns: it runs no `mcp add` or `mcp remove` and sets no `tool_timeout_sec`, and after a Remove it writes nothing. The listing does this only for a row the CLI still lists; a row that reads **Not registered** is left to the next window. When the entries cannot be written, the window opens without its hooks as before, and the daemon's log says why. This release still needs one Update for the bridge's new argument (see Upgrade notes). See [`docs/mcp-setup.md`](docs/mcp-setup.md#registering-from-the-gui).
- **Register, Update, Remove and the rewrite take out Codex CLI's hook trust for the two `UserPromptSubmit` handlers that are gone** (the `[hooks.state."<key>"]` tables whose keys end in `user_prompt_submit:0:1` and `user_prompt_submit:0:2`). The bundled Codex profiles now give each event one handler.
- **A hook written for a profile names that profile's id.** A profile of your own whose hooks call `--hook <id> <Event>` is no longer found by them once its file is renamed: such a hook then does nothing, and the daemon logs a warning. Register again after renaming. The id of a bundled profile changes only in a breaking release.
- **Inside a window, a door given an argument it does not know now reads its input to the end and exits 0**, with one warning in the instance's log that names the flag (never a value). It used to refuse the command line, so the CLI reported a failed hook. A hook written by a later release thus does nothing in this release's windows instead of failing. Outside a window nothing changes.
- **On macOS and Linux, `close_window` ends a window's processes beyond its process group.** The window's watcher hangs the command up, then signals the window's processes with `SIGTERM` and `SIGKILL`, reading the tree again each round. On Linux this reaches every descendant, one that moved itself into another process group or session included, unless it runs as another user or moved itself into another systemd scope; on macOS it reaches the processes in the command's session or process group and their children. A macOS process that put itself into a session of its own and whose parent has already exited cannot be told from your other processes and is left running. A process that does not end even on `SIGKILL` is waited for a few seconds at most and then left, and the daemon's log says how many were. See [`docs/mcp-setup.md`](docs/mcp-setup.md#close_window).
- **On macOS, closing a window no longer leaves behind a process the window's command had put into a session of its own, or one that outlives `SIGTERM`.** This held when a window was closed, when its holder ended unexpectedly, and when the holder ended the window after its watcher had; a hangup or a `SIGTERM` could end the process's parent before yagura had read the tree. The watcher now reads the window's processes first, then hangs the terminal up, and keeps every process it has read in its sweep even once the parent has ended; for the holder that ends a window after its watcher, this holds only while the window's command was still running when the watcher ended. A process whose parent had already exited before the window began to close, including a window's command that exited by itself, still cannot be found. The holder also no longer ends a window's input while the window closes, on macOS and Linux: a command that used to exit with code 0 on the end of its input is now ended by `SIGHUP` or `SIGKILL` and exits with code 1. See [`docs/mcp-setup.md`](docs/mcp-setup.md#close_window).
- **Windows opened from the bundled `codex-cli` and `wsl-codex-cli` profiles start Codex with `--no-daemon`**, so a window's tools run in its own process tree rather than a shared Codex server. The wake, `codex queue`, runs without the flag as before. See [`profiles/README.md`](profiles/README.md#arguments-for-starting-a-window-only).
- **On macOS and Linux the daemon raises its open-file limit as far as the system lets it when it starts**, so a low default (256 on macOS) does not limit how many windows it can keep. The programs it starts, the windows' commands among them, starts with the limit the daemon itself started with, and the daemon's log names the raised limit. On macOS, starting a program now marks only its open descriptors to be closed on exec, so the raised limit does not slow opening a window.
- **In the `yagura-daemon` library API, `control::interrupt_window` takes a third argument, `press`**: the named key (`input_encode::NamedPress`) its bytes were encoded from when they are exactly one, which the window's detector is told of as a press, or `None`.
- **A detection definition with a `[turn_end_key]` table cannot be loaded by an older daemon**, whose windows of that definition then read as `unknown`, so a copy of the new `copilot-cli.toml` kept in the config root's `detection/` folder needs this release. The other way round, an older copy kept there takes the place of the bundled definition and does not get the fix for GitHub Copilot CLI's interrupt (see Fixed): add the bundled `[turn_end_key]` table to it. See [`crates/yagura-daemon/detection/README.md`](crates/yagura-daemon/detection/README.md#turn_end_key).
- **The theme file's palette is now 29 keys, and the built-in colors are new.** `themes.toml` needs 29 keys per theme; `color-primary-hover`, `color-error-hover`, `color-warning-action`, `color-warning-action-hover`, `color-on-warning` and `color-on-warning-action` are no longer read, so a theme may leave them out. A theme file written for earlier versions, with all 35 keys, still loads (a value that is not `#RRGGBB`, or a key yagura does not know, is still refused). yagura now derives its surface, text, line, focus-ring and status colors from the palette itself, so a custom theme restyles the controls too, light themes included. The built-in `dark` and `light` palettes have new values, and with them the colors the daemon answers a window's OSC 10, 11 and 12 queries with, and the cursor color. The default theme is now set in one place, and a `themes.toml` without `default` follows it. That default is now `system`, which follows the OS color scheme; it was `dark`. See [`docs/themes.md`](docs/themes.md).
- **The GUI and the terminal use your operating system's fonts.** The interface takes the platform's UI font and the terminal its monospace font (Cascadia Mono, SF Mono, Menlo, Consolas, DejaVu Sans Mono and so on) instead of `Courier New`; no font is bundled or loaded.
- **A window's status reads the same everywhere and does not depend on color alone.** The status badge shows an icon and a word. **Needs approval** and **Needs input** are now different marks (they looked alike), and Unknown shows its reason as text. The window list and the window header use the same words.
- **Icons are drawn, not typed.** The close, stop, minimize, menu and arrow marks no longer come from the operating system's fonts, so they look the same on every platform.
- **Hints no longer use the browser's `title` attribute.** They appear on keyboard focus as well as on hover and can be dismissed with Escape. Menus open from the keyboard and move with the arrow keys.
- **An interrupt button that cannot act now stays focusable and says why.** For a window whose status is `unknown`, the button no longer drops out of the tab order and its reason can be read; pressing it still does nothing.
- **Buttons and input fields were rebuilt on the new colors**, with a visible focus ring.
- **Values that point at a place show every hidden character written out, as `\u{202E}`, instead of dropping it or drawing it.** This applies to a window's working directory, a room's name (in the window list, the Chat panel and the approval dialog), a ticket workspace's path and name, and the working directory of a window offered for restore. Removing such a character made two places look alike, and drawing one could reorder the path. The approval dialog's body now writes out zero-width and other invisible characters too (U+200B, U+2028, U+2029, U+2060, U+FEFF, ZWNJ, ZWJ and the rest of the default ignorable characters), not only the bidirectional controls, so an approver sees everything that will run; a ticket's body, field values and results follow the same rule. Window names, vendors and other labels still drop them, and also drop U+061C now.
- **Breaking: U+061C (ARABIC LETTER MARK) is refused wherever LRM and RLM already were.** A window name or vendor, a plan or ticket title, the text of `send_message`, a chat post, a handoff, a task's instruction and a ticket's body, field values and results that hold it are refused with the character's position. A profile of your own whose `display_name` holds it is not loaded, and a saved palette for a vendor that holds it is dropped without a message.
- **A window waiting for input after it reported to its living owner no longer counts as "needs you".** When a plan's task window has reported to its owner and nothing new has been given to it since (no keys that may start work, hand-off or confirmed push), its wait is for the owner, not for you. The sidebar's count, the **Needs you** filter and the next-window-needing-you key skip it; its status still reads Needs input. A new instruction, closing the owner, removing the task or deleting the plan ends the exemption, and nominating another owner moves it to the new one.
- **The tab strip is gone; the work area has two views, Focus (the default) and Canvas.** In Focus the current window fills the work area, and it cannot be dragged or resized there. Canvas keeps the floating windows, now drawn as cards with the current one raised. Switch from the view menu in the sidebar header; yagura remembers the choice. `minimize-window` and `toggle-maximize-window` work only in Canvas. See [`docs/keymap.md`](docs/keymap.md).
- **The sidebar draws one row per window,** with its status, name, vendor, and on the right the permission shield, the inbox count and (in Canvas) the minimized mark. Rows that need you or whose status is unknown are drawn in full weight and the rest step back. Interrupt and close moved from the rows to the window's header, which is now the same in Focus and Canvas and says where the window lives, its status in words (an unknown status says why) and its marks. Room and folder headings collapse and show a status summary when collapsed.
- **The sidebar list is one `Tab` stop.** `Tab` lands on the current window's row, the arrow keys, `Home` and `End` move between rows and stop at the ends, `Enter` or `Space` goes to the window, and the next `Tab` leaves the list.
- **Next and previous window follow the rows you see.** While the **Needs you** filter is on they walk the filter's rows in the order shown, and next window needing you visits only the windows that need you. The filtered list is headed by room without reordering its rows, and nothing in it can be reordered, so rows never move under the pointer.
- **The Rail is redrawn, and Windows works.** It sits on the chrome background with a bar at your place; Windows sends the keyboard to the current window's terminal, and Board, Chat and Settings open or close their panels and say whether they are open.
- **A window that ends on its own, or that an agent closes, no longer moves you to another window or moves focus.** A card says which window ended and with what exit code, and offers **Go to** the next window or **New window**. While it is shown, next and previous window start from where the ended window stood and never wrap around; **Go to** shows the next-window key. A window you close yourself still moves you to the next one, and a window opened by another route is added without switching to it.
- **The IPC protocol is now revision 36.** `WindowInfo` and `status_changed` carry an optional `task_report` (`seq` and `state`), left out when the window has none, and a body without it decodes as none (the same as a daemon from before this revision). `state` is `standing`, `instruction` or `no_reader`, and a value this build does not know is read as `unknown`; the side that reads the daemon's mark (Rust) reads a revision 35 body, which has no `state`, as `unknown` in the same way. MCP's `list_windows` answer is unchanged.
- **Interrupting a window (the stop button, or `interrupt_window`) no longer ends the exemption of a task window that has reported** (see above). Stopping a turn hands the window no new work, so its report still stands, as when you press Esc in the window.

### Added

- **yagura tells you from outside its window when something waits for you.** The window title and, on macOS, the Dock badge both show the number of windows that need you plus the pending permission requests. When something newly starts to wait for you (a window asks for a permission, a window's turn ends and it waits for input, or a task window's report has nobody left to read it because its owner is gone, the task was removed or the plan was deleted) and yagura does not have the focus, it asks for your attention. A count that only looks higher because the daemon restarted or the GUI reconnected or reloaded does not ask; the exception is a window that is already waiting on a permission when the GUI starts or reloads, which counts as a newly seen permission wait and asks once.
- **Programs now get keys the traditional format cannot express** (`Ctrl+Tab`, `Ctrl+Shift` with a letter). A Windows window sends keys the way Windows Terminal does: every key in the Kitty keyboard protocol's format when the program asks for it, and otherwise every key in Win32 Input Mode, which ConPTY requests at start (a symbol key outside yagura's fixed key table keeps the traditional format). A WSL window never gets Win32 Input Mode, since `wsl.exe` turns it back into the traditional format with less of the press than yagura's own traditional format keeps; there every key takes the Kitty format when the program asks for it, and the traditional format otherwise. On macOS and Linux every key takes the Kitty format when the program asks for it. See [`docs/keymap.md`](docs/keymap.md#how-keys-reach-the-program).
- **On Windows, `Ctrl+V` with something other than text on the clipboard (an image, for example) is passed to the CLI**, which reads the clipboard itself. Text is still pasted by yagura.
- **`withdraw_message`**, an MCP tool that takes back an envelope you sent with `send_message` or `send_handoff` while it still waits in its window's inbox (`withdrawn`, `under_way` or `not_waiting`). Only its sender may, and no approval is asked: a caller that is no window is the MCP session that sent it, for as long as its connection to the daemon lasts, and `get_window_status`'s `queued_ids` lists its own envelopes too. See [`docs/mcp-setup.md`](docs/mcp-setup.md#withdraw_message).
- **`queued_count` in `list_windows` and `get_window_status`**, how many envelopes and notices wait in a window's inbox, and **`queued_ids` in `get_window_status`**, the ids of those your own window sent that still wait there.
- **`[limits] max_queued_per_sender`** in the playbook, from 1 to 64 (default 8); a value outside that range is warned about and the default kept.
- **Launch profiles take an `[interrupt]` table**: the keys the user's own interrupt writes (`user_keys`), and how an AI stops the CLI (`ai`): its own keys (`ai_keys`), a stop answered at the CLI's stop events through its hooks (`[interrupt.turn]` with `starts` and `ends`, and `[interrupt.stops.<Event>]` with `answer` and `ends_turn`), or `none`. Keys are named `escape` and `ctrl_c`. See [`profiles/README.md`](profiles/README.md#interrupt).
- **A hook door, `yagura-daemon --hook <profile-id> <Event>`**, which does what the named profile's `[hook_events]` table says for the event. It takes `--for-instance` and `--credentials` like the other doors, but no `--skip-if`: the pointers come from the profile. The existing doors (`--emit-status`, `--deliver-context`, `--deliver-take`, `--deliver-wait`, `--report-session`) remain. See [`crates/yagura-daemon/detection/README.md`](crates/yagura-daemon/detection/README.md#structured-sources---emit-status).
- **Launch profiles take a `[hook_events]` table**, one entry per event with `status`, `deliver` (`context`, `take` or `block`), `session` and `when` (the values the hook's input must hold for `deliver` to hand anything over), and a top-level `subagent_pointer`. See [`profiles/README.md`](profiles/README.md#hook-events).
- **Launch profiles take a `[hook_timeout]` table**: the seconds the CLI gives a hook, which the daemon tells a door, and which the profile's hook texts name by placeholder (`{hook_timeout}`, `{hook_timeout.doors.<door>}`, `{hook_timeout.events.<event>}`). See [`profiles/README.md`](profiles/README.md#hook-timeout).
- **`[delivery.output]` takes `block`**, the form a stop's block is printed in, and an output template may carry `{event}`, the name of the event its door runs for.
- **A Claude Code window that has lost its wait is asked to register it again.** When something waits for a Claude Code window that waits for input and no wait is registered -- the daemon ended abnormally and the window outlived it, or the CLI's own time limit for the wait ran out -- the daemon writes the window's wake file once, and the CLI, which watches it, registers its wait again and takes what waits. The list of files to watch is handed over at session start and on each change of directory by `--print-answer`, which needs no daemon. The bundled Claude Code profiles add a `SessionStart` and a `CwdChanged` hook running `--print-answer`, and a `FileChanged` hook matched on `yagura_wake` running `--deliver-wait`. See [`docs/mcp-setup.md`](docs/mcp-setup.md#how-the-daemon-delivers-text).
- **A door that needs no daemon, `yagura-daemon --credentials <path> --print-answer <Event>`**, which prints the answer the window's open wrote beside its credentials file, and **`answers` under `[hooks]`**, the texts it prints, which may name `{wake_paths}`. See [`profiles/README.md`](profiles/README.md#answers-a-hook-prints-without-the-daemon).
- **`state_base` under `[host_paths]`**, the command that prints where a CLI in another environment keeps its state, for its wake file; the bundled `wsl-claude-code` declares it. The daemon makes the wake file's folder as the window opens, before its CLI starts, so a WSL window can be woken from the first time it is asked; a window whose folder cannot be made opens without a wake file. See [`profiles/README.md`](profiles/README.md#host-paths).
- **Launch profiles take a `[launch_overlay]` table, and `{daemon}` as a whole `[command]` element**, for a settings layer that keeps the window's credentials from the CLI's tools; a CLI in another environment makes it through the new door `yagura-daemon --launch-overlay`. See [`profiles/README.md`](profiles/README.md#launch-overlay).
- **`[credentials]`, `[mcp]` and `[hooks]` may be written per operating system**, with the keys `[command]` uses. See [`profiles/README.md`](profiles/README.md#mcp-injection).
- **`[mcp_registration.status]` takes `args_line`**, and `args_pointer` is now compared: a row whose registered bridge arguments differ from the ones this daemon registers reads as differing, with `args` in `differs_in`. See [`profiles/README.md`](profiles/README.md#mcp-registration).
- **`[mcp_registration.toml_set.entries]` takes `retired`**, the keys under `under` an earlier version wrote and this one no longer does, chosen per operating system like the entries. Register, Update and Remove take them out. See [`profiles/README.md`](profiles/README.md#mcp-registration).
- **On macOS and Linux every window has a watcher, `yagura-watcher`**, a small single-threaded process its holder starts, which starts the window's command and ends the window's processes when the window closes. If the holder ends unexpectedly, the watcher ends them; if the watcher does, the holder does; and if both end, the daemon ends what it can still reach from the window's command, at once or the next time it starts. A window whose watcher cannot be started does not open (`spawn_failed`). The macOS and Linux packages install `yagura-watcher` beside `yagura-holder`; the Windows package has none, as a window's Job Object ends its processes there. See [`docs/mcp-setup.md`](docs/mcp-setup.md#when-a-windows-holder-ends-unexpectedly).
- **Launch profiles take `launch_only` under `[command]`**, argv elements added to a window's spawn only: a wake by command, the argv a listing reports and a registration builds on, and a model listing go without them, and a restored window gets them again from the profile. Each element must be a non-empty string without a NUL, as in `[credentials] launch_args`. See [`profiles/README.md`](profiles/README.md#arguments-for-starting-a-window-only).
- **A `yagura-locale` crate**, which the daemon alone depends on, now holds `preferred_locale`, `PreferredLocale` and `locale_exists` (see Removed), so the holder and the watcher do not link macOS's CoreFoundation.
- **In the `yagura-os` library API, the parts a Unix window's holder and watcher are built from**, all outside Windows. `pty::open`, `pty::leader_command` and `pty::start_leader` (with `PtyPair` and `LeaderCommand`) open a terminal and start a command on it in another process. `TREE_END_LIMIT`, and in `platform_unix` (Linux and macOS) `TreeEnd` with `TreeEndHooks`, `TreeEndRest`, `SignalTarget`, `ProcessRow` and `window_members`, end a window's process tree in bounded rounds. `platform_unix` also gains `lock_endpoint_blocking`, `remove_endpoint_files_under_lock`, `EndpointLock`, `endpoint_lock_path` and `SocketListener::lock_descriptor` for an endpoint's lock; `socket_pair`, `send_with_descriptors`, `receive_with_descriptors`, `spawn_watcher`, `take_inherited_socket` and `peer_has_closed` for the holder's link to its watcher; `raise_descriptor_limit` and `spare_descriptors`; and `block_child_signal`, `block_watcher_signals`, `wait_child_signal`, `ChildChange`, `take_child_change`, `continue_child`, `hang_up_child`, `kill_child`, `unreaped_exit`, `reap_exited_child`, `WatcherWait` and `WatcherEvents` for following a child without reaping it.
- **A detection definition takes a `[turn_end_key]` table**: `key`, the key (`ctrl_c` or `escape`) whose press ends the CLI's turn, and `shown`, a regex the bottom rows show while that key stops a turn. A press of the key, from the GUI or written by `interrupt_window`, closes the window's turn once the screen has shown `shown` since the last submission, and reports do not open a turn again until the next one starts. The bundled `copilot-cli` definition declares Ctrl+C. See [`crates/yagura-daemon/detection/README.md`](crates/yagura-daemon/detection/README.md#turn_end_key).
- **A Needs you filter, a view menu and a count in the sidebar header.** The filter lists the windows that need you, keeps its rows still until you act, and says so when nothing needs you; the view menu switches between Focus and Canvas and tiles the windows in Canvas.
- **Sidebar rows can be reordered** within their room by dragging, or by **Move up** and **Move down** in the row's menu (opened by right-click, `Shift+F10` or the context menu key). Reordering is not offered while the Needs you filter is on.
- **A card on a window's row** shows its name, the vendor and folder it runs in and why its status is unknown. It opens on pointing, and on keyboard focus only when the focus came from the keyboard.
- **An empty work area** says so and offers **New window**, the windows of your last session with when they were saved, and the main shortcuts with their current keys.

### Removed

- **Breaking: Antigravity CLI is no longer supported.** yagura no longer ships the `antigravity-cli` and `wsl-antigravity-cli` launch profiles or the `antigravity-cli` detection definition, so Antigravity CLI has no entry in the new-window dialog, no rows in Settings > Integrations and none in the Models tab, and the docs no longer describe configuring it. Google's [Antigravity terms](https://antigravity.google/terms/) (section 6) treat accessing the service through third-party software as a breach that can get the account suspended or terminated, and its [FAQ](https://antigravity.google/docs/faq/) says that wrapping `agy` inside third-party applications is not supported under consumer plans; a suspension can also take away the other services signed in to with the same Google account. yagura does not stop any command from running, but we strongly recommend that you do not run `agy` signed in with a consumer account inside yagura. See [`README.md`](README.md#antigravity-cli-is-not-supported), and Upgrade notes for what to remove.
- **Breaking: the `send_keys` MCP tool**, and the IPC request `send_keys` with its answer `keys_sent`.
- **Breaking: the MCP error `not_written`.** `send_message` is no longer refused as `no_composer` either; a window that takes no text through doors answers `undelivered_no_delivery`, and `no_composer` remains only for a launch whose profile declares no `launch_prompt`.
- **The daemon's typing into a window**: nothing is taken back out of a composer any more, and the delivery marks an older daemon left for a typed delivery are dropped with a warning.
- **`send_message`'s `mode` argument.** It took only `"immediate"`, the way the daemon used to type a message into the window at once; a message now always waits in the window's inbox until the CLI takes it, so there is nothing left to choose. A call that still sends `mode` is not refused: the argument is ignored.
- **The `submit_child` test fixture binary** of the `yagura-daemon` crate.
- **The `YAGURA_CLOSE_SETTLE_MS` environment variable**, and `DaemonConfig::close_settle_ms` and `resolve_close_settle_ms` from the `yagura-daemon` library API. `close_window` no longer waits a fixed budget for the window's status (see Fixed).
- **`yagura_os::locale`**, whose `preferred_locale`, `PreferredLocale` and `locale_exists` moved unchanged to the new `yagura-locale` crate.
- **On macOS and Linux, `yagura_os::pty::spawn`**, with `PtySpawn`, `PtySpawnError`, `PtyChild` and `PtyKiller`. They remain on Windows; a Unix window starts through `pty::open` and `pty::start_leader`.
- **The tab strip and the maximized-as-tab mode.**
- **Two items of the window menu that did nothing.**

- **`auto_approve = ["send_keys"]`** loads with a warning and approves nothing.
- **In detection definitions, the `[input]` table and `[composer]`'s `placeholder` and `right_border`** load with a warning that names each key, and are not used. `schema_version` is unchanged. See [`crates/yagura-daemon/detection/README.md`](crates/yagura-daemon/detection/README.md#schema).

### Fixed

- **A window whose CLI does not report its approvals (GitHub Copilot CLI) no longer reads as `waiting_input` while the tool you allowed runs, when its approval box, or a screen its definition declares `unknown`, was up for 5 seconds or more.** The time the screen waits on you no longer counts as the turn's silence or as time without a report. See [`crates/yagura-daemon/detection/README.md`](crates/yagura-daemon/detection/README.md#what-a-report-means).
- **A GitHub Copilot CLI 1.0.112 window no longer reads as `waiting_input` while its turn runs, and a Muse Code 1.4.20 window no longer does while a command with much output runs.** The `copilot-cli` definition now reads the footer's `<key> interrupt` hint whatever the key (1.0.112 shows `ctrl+c interrupt`; the 1.0.101 hints still read as running), including while Copilot waits for background shells. The `muse-code` definition also reads the `(ctrl+b to send to background)` hint a running command leaves on the screen once its output pushes the turn's status line out of reach.
- **Right after a restart, a running window no longer gets a false "status reports aren't arriving" mark and warning.** A window the daemon takes back is now measured from its first running turn after the one it was in has ended, not from a turn already under way.
- **A message for a Claude Code window that waits for input no longer waits for its next turn when its wait is gone.** After a daemon that ended abnormally, or once the CLI's own time limit for the wait ran out, the daemon now asks the CLI to register its wait again (see Added).
- **`close_window` now replies, once the daemon has observed the child's exit, only after the window reports `exited`**, instead of waiting a fixed budget for it, so the GUI no longer brings back the pane of a window it has just closed. A window whose detection had stopped now reports `exited` once its process ends, whether it was closed or ended by itself; before, it stayed `unknown`, kept a pane, and kept counting against the window limit. See [`docs/mcp-setup.md`](docs/mcp-setup.md#close_window).
- **A CLI's hook that reports right after the window starts is no longer refused while the window is still opening.** Its status report, and its requests for the window's messages, now wait for the window to finish opening, as the CLI's own connection already did.
- **In the GUI, what you type next goes to the window you picked or acted on.** Picking a window in the sidebar, its frame or its maximize button, and closing a dialog about the window in front (interrupt, close, rename), now move the keyboard into that window, so `Enter` no longer presses the interrupt button again. After an approval or another dialog, focus returns to where you were; after a minimize or a close, to the current window when focus had nowhere left to type into. A window that comes to the front on its own, such as one an AI opened, does not take focus. See [`docs/keymap.md`](docs/keymap.md#where-typing-goes-after-you-pick-a-window-or-close-a-dialog).
- **After the daemon restarts, a window no longer stays at "Cannot reach the daemon" and no longer ignores what you type.** The next window-list poll attaches it again, and it comes back as it was last asked to be, even meanwhile: shown or hidden, at its size and in its colors.
- **Keys typed while a window reconnects now reach it, in the order they were typed, once it is back.** Before, they were dropped. A window that cannot be reached still drops them.
- **After the daemon restarts and takes a window back, the GUI no longer keeps showing the window's old status.** A window's `status_rev` now comes with the `status_boot` it was counted in, and the GUI compares the pair `(status_boot, status_rev)`, so the next daemon's lower count no longer reads as older.
- **A GitHub Copilot CLI window no longer stays `running` after you cancel a turn with Ctrl+C or the window's interrupt button.** Copilot runs no hook when a turn is cancelled and keeps redrawing its screen while it waits, so the window used to stay `running` for 5 seconds or more, up to 2 minutes. The press now closes the turn at once, on a version whose footer shows `ctrl+c interrupt` while a turn runs (1.0.112). A turn cancelled with Esc twice is not covered: the window still stays `running` until its output has been quiet for 5 seconds, or longer while Copilot redraws its screen. See [`crates/yagura-daemon/detection/README.md`](crates/yagura-daemon/detection/README.md#limits).
- **In the approval dialog, the second and later requests of a queue now start with the focus on Deny too.** The dialog stays open while its queue advances, so the next request kept the focus left on the previous one, and Enter could approve it.

### Security

- **The SQLite the daemon bundles is now 3.54.1** (it was 3.53.2), which fixes RUSTSEC-2026-0459. It comes with `rusqlite` 0.41, the first release that uses a `libsqlite3-sys` bundling it.

### Upgrade notes

- **Press Update once for each registered CLI in Settings > Integrations.** The bridge is now registered with `--profile <id>`, so a row registered by an earlier release reads as **Registered with different arguments**. Until it is updated, a window opened from a profile that gives its CLI hooks does not take that registration's bridge as itself: its tools run as `External`. On Windows the same Update also writes the Muse Code hooks this release adds.
- **Open again the windows you opened before updating.** Their hooks and bridges were started by the earlier release. In particular: a Claude Code window keeps waiting for the CLI's next event, as before, since it has no wake file; a Grok Build window stops reporting its status, taking part in delivery and calling yagura's tools as itself, since it has no launch overlay; a bridge that reconnects after the daemon restarts declares no profile and runs as `External`; and an AI's interrupt can answer `stop_requested_unconfirmed` until its hooks reach the new daemon.
- **The bundled Claude Code profiles' hooks changed** (`--hook claude-code <Event>`, and the wake file's hooks). They are passed with each launch, so a newly opened window has them.
- **On macOS and Linux, remove an earlier Muse Code registration by hand.** Every `muse-code` launch now passes its own server, and a server of the same name in `~/.config/muse/settings.json` makes Muse refuse it, so the window opens without yagura's server. Remove `mcpServers.yagura` (or `yagura-<instance>`), and `managed_hooks_path`, `managed_hooks_env_vars` and `yagura-managed-hooks.json` if they are yagura's; there is no Muse Code row to remove them from any more.
- **An AI can no longer interrupt a Codex CLI window**: the call is refused as `interrupt_unsupported`. Close the window, or interrupt it yourself.
- **A profile of yours with `skip_if` in `[hook_events]`** loads when every event writes the same pointer, with a warning naming `subagent_pointer`. When the pointers differ, the profile is not loaded, and a file of yours that lays such a table over a bundled profile takes that profile out too: its windows stop reporting their status and taking part in delivery until you write one `subagent_pointer` instead.
- **`--emit-status running --skip-if <pointer>`, and `waiting_approval`, now report for a subagent's hook too.**
- **An older daemon leaves out a profile of your own that uses a key this release adds** -- a `[hook_events]` table, `retired` under `[mcp_registration.toml_set.entries]`, `launch_only` under `[command]`, `subagent_pointer`, `[hook_timeout]`, `[interrupt]`, `[launch_overlay]`, `when` or `deliver = "block"` in an event, `max_bytes` or a `block` output under `[delivery]`, `answers` under `[hooks]`, `state_base` under `[host_paths]`, `args_line`, or a `[credentials]`, `[mcp]` or `[hooks]` table written per operating system -- with a warning. See [`profiles/README.md`](profiles/README.md#upgrading).
- **Going back to an older daemon with a Claude Code window this release opened**: the older `yagura-daemon` does not know `--print-answer`, so those hooks print nothing (and log a warning), and since it never asks the CLI to register its wait again, delivery waits for the CLI's next event, as it did. A hook of a window an older release opened gets nothing from this release's doors, which hand an older door's read nothing to print; open the window again.
- **Updating replaces the daemon the way it did before.** A wait that outlives the daemon is something this release adds for a daemon that ends without closing its windows; it is not a promise about an update.
- **Running a release before this one beside this one, as the same user, breaks the older instance's Muse Code and Codex CLI hooks.** These two CLIs keep one set of hooks for every instance, and once this release has written them in the new form, the older daemon cannot read them: in its `muse-code` windows the hooks fail, and it opens its Codex CLI windows without hooks. Update the older instance to put it right. Grok Build keeps entries of each instance's own and is not affected.
- **If you used Antigravity CLI with yagura, close its windows before updating, then remove what yagura left for it, at your own terminal.** This release has no Antigravity CLI profile, so a window still open when the daemon is replaced keeps running with no profile behind it: it reads as `unknown`, takes no part in delivery, and its hooks do nothing. Then:
  - delete the `yagura` entry (`yagura-<instance>` for a named instance) from `~/.gemini/config/hooks.json`, leaving the other entries as they are;
  - remove the MCP registration with `agy mcp remove yagura` (`yagura-<instance>`), or delete that server from `mcpServers` in `~/.gemini/config/mcp_config.json`;
  - if you registered from a WSL row, do both again on the `~/.gemini` inside the distribution;
  - delete `antigravity-cli.toml` and `wsl-antigravity-cli.toml` from the `profiles` folder of the config root, if you have them: a file that holds only your changes to a bundled profile no longer loads, and keeps a warning in the new-window dialog;
  - change any role in `roles.toml` that names either profile: a window opened through it is refused as `profile_not_found`.

  There is no Integrations row to remove them from any more. See [`docs/mcp-setup.md`](docs/mcp-setup.md#removing-yagura-from-antigravity-cli).
- **Restoring a session no longer reopens a window from its saved argv when its profile cannot open it.** A window recorded with a profile that is gone, disabled, no longer runs on this operating system or does not take a recorded value is left unopened, and one notice names every window the restore could not open, each with the daemon's reason (`Not restored (2): review-pane: unknown launch profile; build-runner: the launch profile is disabled`). Before, such a window was started again from the argv it was recorded with, without the profile's hooks, MCP server or credentials, unless its profile was disabled. A window opened from a raw command is restored from its saved argv as before. See [`profiles/README.md`](profiles/README.md#restoring-a-window-opened-from-a-profile).

## [0.3.0] - 2026-10-29

### Changed

- **The IPC protocol is now revision 29.** The ticket requests (`list_ticket_workspaces`, `list_tickets`, `get_ticket`, `create_ticket`, `update_ticket`, `add_ticket_result`, `set_milestone`) and their replies are new, as is the push `ticket_changed`, which the daemon sends to every approver after a ticket is written. `create_plan` takes an optional `ticket` and `PlanInfo` carries it; both are left out when absent. A client sending a ticket request checks the daemon's revision first.
- **The session database is now at schema 016, which cannot be undone.** A database this version has opened is refused by an older daemon (its `user_version` is newer than that daemon knows). Run the GUI and the daemon from the same release.
- **The IPC protocol is now revision 30.** A registration row (`McpRegistrationRow`) carries the profile's `notice`, left out when absent, and `ProfileCapability` has the new value `launch_context`, the launch capability a profile's limits name when the room's introduction cannot be passed on the command line. A peer that predates them reads a row without a notice, and reads `launch_context` as an unknown capability.
- **An older daemon leaves out a profile of your own that uses a key this release adds** (`env` under `[model]` or `[effort]`, `launch_context` under `[delivery]`, `notice` under `[mcp_registration]`, `items` and `name` under `[mcp_registration.status]`), with a warning, and takes a `{server}` in a `json_entry` `file` as part of the file name. A detection definition of your own with `right_border`, or with a `region = "screen"` rule, fails to load there. See [`profiles/README.md`](profiles/README.md#upgrading).
- **A window opened from the `claude-code`, `copilot-cli`, `wsl-claude-code`, `wsl-copilot-cli` or `wsl-muse-code` profile no longer has `YAGURA_WINDOW_ID` and `YAGURA_STATUS_TOKEN` in its environment.** Its hooks and its MCP bridge are handed a credentials file in their arguments instead (`--credentials <path>`), so a CLI that one of the window's tools starts, and a script run in the window, can no longer report as that window: its hooks and bridge are outside any window. A script of your own that read `YAGURA_STATUS_TOKEN` in such a window no longer finds it. The file is removed when the window's child exits. `WSLENV` no longer names the two variables for these WSL windows.
- **In a `codex-cli` or `wsl-codex-cli` window, the tools Codex runs get `YAGURA_WINDOW_ID` and `YAGURA_STATUS_TOKEN` as empty values**, through `shell_environment_policy.set`. Codex itself keeps the real values, because a changed hook command would void the trust hashes it recorded.
- **An empty `YAGURA_WINDOW_ID` or `YAGURA_STATUS_TOKEN` now counts as unset.** A hook door whose pair is empty is outside any window and does nothing; before, it sent the empty id and the daemon refused it.
- **An older daemon leaves out a profile of your own that has a `[credentials]` table**, with a warning. See [`profiles/README.md`](profiles/README.md#upgrading).
- **After updating, press Update for Antigravity CLI (and its WSL row) in Settings > Integrations of each instance.** The bundled hooks changed, so the hooks entry recorded earlier no longer matches; until it is written again, that instance's Antigravity CLI windows are not handed text, and its entry of the older form still reaches the daemon of any other instance's window it runs in.

### Added

- **Grok Build is supported**, with two bundled launch profiles, `grok-build` (Windows, macOS and Linux) and `wsl-grok-build` (Windows, running Grok Build inside WSL), and a `grok-build` detection definition. A window reaches yagura once yagura is registered with Grok Build from Settings > Integrations, which runs `grok mcp add` and writes a hooks file of the registration's own in `~/.grok/hooks`; Grok Build has no launch argument for either. Such a window reports its status from hooks, takes part in chat and handoffs (the room's introduction is given with `--rules` at launch, and waiting texts are taken after a tool call or typed while the window waits for input), and reads Grok Build's folder trust prompt and permission box as `waiting_approval`. The model is passed as `GROK_DEFAULT_MODEL`, since `-m` saves it as the user's default. Claude Code's and Cursor's hooks and MCP servers, which Grok Build also runs, are switched off in yagura's windows. While registered, Grok Build asks about folder trust in every folder outside the home directory, in sessions you start yourself too; the Integrations row says so. Checked with Grok Build 1.0.70 on Windows and in WSL. See [`docs/mcp-setup.md`](docs/mcp-setup.md#configuring-grok-build), which also lists what does not work.
- **A launch option can set environment variables.** `[model]` and `[effort]` take `env` beside or instead of `args`, its values holding `{value}`, laid over the profile's `[env]` only for a launch that asks for the option. See [`profiles/README.md`](profiles/README.md#launch-options).
- **A profile can keep a window's credentials out of its environment.** The new `[credentials]` table has `mode`, `"env"` (the default) or `"launch"`, and `launch_args`, arguments added to the launch only. In `"launch"` mode the daemon writes a file of the window's own holding its id and token, readable by its owner only, and `[mcp]` and `[hooks]` name it with the new `{credentials_file}` placeholder. See [`profiles/README.md`](profiles/README.md#credentials).
- **A hook door and `yagura-mcp` take `--credentials <path>`**, the credentials file to read the window from when the environment does not hold both variables, non-empty. The doors take it at most once. See [`crates/yagura-daemon/detection/README.md`](crates/yagura-daemon/detection/README.md#structured-sources---emit-status).
- **A hook door takes `--skip-if <JSON Pointer>`**, and does nothing when the hook's input has a value there, for a CLI that runs the same hooks in its sub-agents' sessions. Every door now reads its input to the end, and outside a window a door no longer reads its other arguments, so a hook written for a newer daemon stays silent there under an older copy. See [`crates/yagura-daemon/detection/README.md`](crates/yagura-daemon/detection/README.md#structured-sources---emit-status).
- **A hook door takes `--for-instance <server>`**, the registration name its hook was written for, and inside a window whose instance registers under another name it does nothing, before reading its other arguments. A hook that registration writes into a CLI's own settings runs in every session of that CLI, once for each instance registered there, so the bundled Antigravity CLI and Grok Build hooks pass `--for-instance {server}` and another instance's hooks stay silent in a window. See [`profiles/README.md`](profiles/README.md#hooks-of-other-instances).
- **`[delivery]` takes `launch_context`**, the arguments that hand a CLI the room's introduction when it starts (`{context}`), for a CLI whose session-start hook does not reach its model. They are added only for a window that takes part in chat, and left out, with the limit listed, when the program is a Windows `.cmd` / `.bat` file. See [`profiles/README.md`](profiles/README.md#delivery).
- **`[mcp_registration]` takes a `notice`**, one line the Integrations row shows, for an effect the user should know of before registering. Its `status` takes `items` and `name`, to read a CLI that lists its servers as an array and shows none by name, and a `json_entry` `file` may carry `{server}`, giving each instance a file of its own. See [`profiles/README.md`](profiles/README.md#mcp-registration).
- **A detection rule takes `region = "screen"`**, matched against every row of the screen, for text whose distance from the bottom changes with the window's height. The `grok-build` definition reads Grok Build's folder trust prompt by its question this way. See [`crates/yagura-daemon/detection/README.md`](crates/yagura-daemon/detection/README.md#what-patterns-are-matched-against).
- **A detection definition's `[composer]` takes a `right_border`**, a regex matching the border a CLI draws at the right end of its input line, cut off before the line is read. See [`crates/yagura-daemon/detection/README.md`](crates/yagura-daemon/detection/README.md#composer).

- **A ticket board for each repository.** Six MCP tools, `list_tickets`, `get_ticket`, `create_ticket`, `update_ticket`, `add_ticket_result` and `set_milestone`, let an agent keep tickets in the workspace of its window (the git repository, or the directory outside one). Numbers start at 1 per workspace; results are append-only; a ticket is never deleted. A window reaches only its own workspace's tickets, and the tools are not put through the approval gate. See [`docs/tickets.md`](docs/tickets.md) and [`docs/mcp-setup.md`](docs/mcp-setup.md#tickets).
- **`tickets.toml` defines the board's states and fields.** The order of the states is the order of the board's columns, and a state may require fields: a ticket cannot be written into it without a value for each. That is the only rule yagura enforces; the file's `guide` and descriptions are shown to the agent as the board's rules. The daemon finds it by `--tickets`, then `YAGURA_TICKETS`, then the config root, and reads it again at every request. The GUI places a reference file (`todo`, `in-progress`, `done`, `considering`, `on-hold`, `cancelled`) on first launch and never overwrites an existing one; it also defines an optional `spec` field, required by no state, that names the repository file and section a ticket's specification lives in, and its `guide` asks the agent to keep the specification there rather than in tickets.
- **`create_plan` takes an optional `ticket`**, and `get_plan` and `get_ticket` report the link in both directions. Making a plan does not change the ticket's state.
- **The Plans panel has a Tickets tab**, now the first and the one it opens on. It shows a workspace's tickets in a column per state, and a ticket's description, fields, results and plans. It only shows: tickets are edited by agents through MCP. Opening the panel does not mark a plan as seen; showing the Board tab does.
- Limits: 256 workspaces with tickets, 10,000 tickets per workspace, 256 results per ticket and 64 milestones per workspace.

### Fixed

- A WSL row in Settings > Integrations read the Windows CLI's own settings in your Windows home folder as its project's, so it could show as registered, or registered to a different bridge, when nothing was registered in WSL, and its Remove could take yagura out of the Windows CLI's settings (seen with Grok Build). Every command a registration row runs -- add, remove, the state read, the path conversion and the file tools -- now starts in an empty folder the daemon keeps under the instance's state folder rather than in your home folder, so no project's settings are read as the CLI's registration. The listing a window reads to turn off the other instances' registrations now runs in the window's own working directory, so a registration in that project is turned off too.

### Security

- **A CLI started by a tool of a window can no longer report as that window** in the bundled profiles listed under Changed: its environment holds no window id or token, so its hook doors and MCP bridge are outside any window. In `codex-cli` and `wsl-codex-cli` the tools Codex runs see the two variables empty. Still open: `grok-build`, `antigravity-cli`, the native `muse-code` (every operating system), `shell` and the WSL variants of the first two keep the credentials in the environment: the hooks of the others are written once into the CLI's own settings by a registration, which has no place for a per-window path, and `shell` has no hooks to hand a file to. They move to a file once their CLI can take its hooks and MCP server at launch, or can set the environment of the tools it runs.
- `rustix` is updated to 1.1.6 for [GHSA-jh2m-fhpj-3vr7](https://github.com/bytecodealliance/rustix/security/advisories/GHSA-jh2m-fhpj-3vr7). The advisory is in its extended-attribute getters, which none of the crates yagura builds with call, so yagura was not exposed. `rustix` is built only on Linux and macOS.
- `sha2` is updated to 0.11, so the daemon and `yagura-os` no longer use `block-buffer` 0.10, which [GHSA-qwgh-2vcv-g2f7](https://github.com/advisories/GHSA-qwgh-2vcv-g2f7) affects. Tauri's build-time code generation still uses it while building the GUI; it is not part of the installed app.

## [0.2.0] - 2026-10-24

### Changed

This release changes how yagura hands text to a CLI, and with it several MCP and IPC values. Anything that reads them needs updating.

- **Text yagura sends of its own accord is no longer typed into the receiving CLI's input line.** Handoff envelopes, the chat announcement and chat posts, and the task, plan and report notices go into the window's inbox, and the CLI takes them through its own hooks, its start-up request, or a command that queues a message on its session. The one exception is a CLI whose profile declares no way to wake it (the bundled Antigravity CLI and GitHub Copilot CLI profiles), which is still typed while the window waits for input. `send_message` still types, as before. See [`docs/mcp-setup.md`](docs/mcp-setup.md#how-the-daemon-delivers-text).
- **`send_handoff`'s `delivery` is now `taken`, `undelivered_timeout` or `undelivered_no_delivery`.** `confirmed`, `unconfirmed`, `not_observed` and `not_written` are gone from this reply, so a client that matches them must change. `taken` says the receiving CLI took the envelope; `undelivered_timeout` says nothing took it within the new `[limits] handoff_delivery_timeout_secs` (default 120) and the envelope was withdrawn; `undelivered_no_delivery` says the window was not opened from a profile that declares how its CLI is handed text, and is answered before the approval decision. `not_written` remains an error code of `send_message`.
- **`read_chat`'s delivery states are now `pending`, `taken`, `undelivered_unknown`, `undelivered_halted`, `undelivered_exhausted` and `undelivered_restart`.** `confirmed`, `unconfirmed`, `not_observed`, `not_written` and `write_failed` are gone. A post to a window whose status is `unknown` now waits (`pending`) instead of being recorded `undelivered_unknown`, which now means the window ended first.
- **Chat delivery records saved by 0.1.0 are removed when the database is upgraded.** They are in the old vocabulary, which recorded what was typed into the input line rather than whether the CLI took the message, so they are not converted. The messages themselves are kept; posts made before the update no longer show a delivery state. The database now refuses a delivery state outside the current vocabulary.
- **A handoff that opens a new window from a `profile` is approved once, before anything starts.** One decision covers the start and the envelope, and the envelope is the CLI's first request; it used to be approved a second time after the window was ready. It skips the dialog only when both `open_window` and `send_handoff` are in `[approval].auto_approve`. There is no readiness wait any more: the reply is `taken` once the process is started, and `window_not_ready` is no longer returned: `yagura-mcp` no longer knows the code, so a daemon left running from before the update that still answers with it shows up as `internal`.
- **A profile must declare `launch_prompt` to be used for a handoff that opens a window or for a task window with an instruction**; otherwise the call is refused as `no_composer` before anything starts. Through a Windows `.cmd` / `.bat` file it is refused as `unsupported`.
- **Which windows take part in chat, and receive handoffs, is decided by the profile.** A window takes part when it was opened from a profile that declares the new `[delivery]` table and its hooks were put in place; a detection definition's `[composer]` and `[input].probe` no longer decide it. `[chat] intro` is now read by the CLI when it starts instead of being posted, and `chat_delivery_max` counts only chat posts being typed into windows. `[limits] handoff_ready_timeout_secs` now bounds only a typed write waiting for its window to finish starting up.
- **Launch profiles have a new `[delivery]` table**, and the bundled profiles declare it and add hooks for it. The table has no `session_pointer` or `wake_timeout_secs` key; writing either is an error. See [`profiles/README.md`](profiles/README.md#delivery).
- **The IPC protocol is now revision 23.** `ProfileInfo` carries `unavailable_kind` and `unavailable_guidance`, a structure of `text`, `command` and `url` (a profile's `[delivery.shim_guidance]` table; `text` is required, `url` is `https` only), and there is a new availability reason: a profile that wakes its CLI with a command is unavailable when its program is a Windows `.cmd` / `.bat` file.
- **The IPC protocol is now revision 24.** The daemon pushes the new `chat_participants_changed` message to every approver when a chat room appears or who takes part in one changes. A client that does not know it can ignore it.
- **On Windows, Codex CLI must be the standalone build, not the npm package.** The daemon wakes a waiting Codex CLI by passing text to `codex queue` on the command line, which the npm package's `.cmd` launcher cannot carry, so the `codex-cli` profile is listed as unavailable until the standalone build is first on `PATH`.
- **After updating, press Update for Codex CLI and Antigravity CLI in Settings > Integrations.** The bundled hooks changed, so the hook trust and the hooks entry recorded earlier no longer match; until they are written again, a Codex CLI window gets no hooks and an Antigravity CLI window is not handed text.
- **A window's name is now unique among the running windows.** Names are compared the way chat mentions are (case-insensitive, `-` and `_` the same), a window that has exited no longer holds its name, and the names chat reserves (`user`, `parent`, `all`) cannot be used. `open_window`, `open_task_window`, `send_handoff` (with `profile`) and renaming a window refuse a name that is taken with the new error `name_taken`, and a default name (a profile's display name, a command's file stem, a task's title) that is taken gets a number: `Claude Code`, `Claude Code 2`, `Claude Code 3`. The output of `open_window`, `open_task_window` and `send_handoff` carries the new `name` key, the name the window actually has. A client that does not know `name_taken` sees it as an unknown error code. A GUI older than this release restoring a session is refused for a window whose name a running window already carries.
- **In the app, restoring a session numbers a window whose name a running window already carries** instead of having it refused, and the Rename window dialog now waits for the daemon: it closes once the window has the new name, and otherwise stays open and shows why, so the name can be corrected in place. The Add a window dialog adds, under a taken name, that leaving the name empty gets a numbered one.
- **A `"` is no longer accepted in a window name**, a profile's `display_name` or a plan task's `title`, because it ends a quoted `@"..."` mention. A profile that already contains one stops loading until it is edited; a plan still loads, but a task whose title contains one cannot open its window without a `name`, and the plan cannot be updated until that title is changed. The label in a model listing and a registration `group` are not window names and still accept it.
- **The IPC protocol is now revision 25.** The open requests `open_window` and `open_window_from_profile` take `on_name_taken` (`refuse`, the default, or `number`), the error code `name_taken` is new, and `window_opened`, `task_window_opened` and `handoff_sent` carry `name`. Every addition is optional on the wire.
- **The IPC protocol is now revision 26.** The approver requests `clear_chat_room` and `delete_chat_room` (answered with `chat_room_cleared` and `chat_room_deleted`), the push `chat_history_cleared`, the error code `room_in_use`, and `ChatRoomInfo.has_open_windows` are new. A message's `seq` now keeps counting up when a room's history is cleared or the room is deleted and re-created.
- **Color queries are answered from the moment a window opens, not once the GUI shows it.** A program asking for the terminal's colors (OSC 10, 11 and 4) gets the colors the GUI last said it would draw a new window with: the theme assigned to the window's vendor in `themes.toml`, else the app theme. The daemon keeps them in its database across restarts, and an instance whose GUI has never run answers with the built-in dark theme. A CLI that draws differently depending on that answer, such as GitHub Copilot CLI, now draws the same screen in a window opened by a handoff or an MCP call while no GUI shows it as in one opened from the GUI. A window's own theme override still applies once the window is shown.
- **The IPC protocol is now revision 27.** The GUI sends the new `set_default_palettes` (not answered) with those colors; a palette must hold 16 ANSI colors and at most 256 vendors may be given one, or it is refused as `invalid_argument`. The session database gains a table for them.
- **A launch profile's `[mcp_registration]` table no longer takes `bridge_probe`; the conversion moved to the new top-level `[host_paths]` table, as `convert`, with `{path}` in place of `{bridge}`.** How a path is seen from the CLI's environment is one fact about the whole profile, so one table now serves both registration and launch. A profile of your own that still has `bridge_probe` is left out of the profile list with a warning until it is changed: remove the `bridge_probe` line from `[mcp_registration]` and add a table of its own, `[host_paths]`, holding `convert = ["wsl", "-e", "wslpath", "-u", "{path}"]` (your own command, with `{bridge}` written as `{path}`). The bundled WSL profiles already use it. See [`profiles/README.md`](profiles/README.md#host-paths).
- **The IPC protocol is now revision 28.** A registration row (`McpRegistrationRow`) may have no command of its own: `add` and `remove` are optional and left out when absent, and `hook_entries` is renamed `entries`, since it now lists every entry a registration writes into a CLI's files. `McpRegistrationStatusInfo` carries `refused_by_claim`, the entry whose other value makes Register and Update refuse, and `ProfileInfo` carries `limits`, what an available profile cannot do on this host. **Run the GUI and the daemon from the same release**: the daemon cannot tell how old its peer is, and a GUI older than this revision that receives a row without a command (Muse Code's) cannot read the Settings > Integrations list at all.
- **A launch profile's `[delivery.shim_guidance]` table is now the top-level `[shim_guidance]` table**, because it now also tells a user what to do about a launch option or a start-up request a Windows `.cmd` / `.bat` program cannot pass, not only about a wake command. A profile of your own that still has `[delivery.shim_guidance]` is left out of the profile list with a warning until it is changed: rename the table heading `[delivery.shim_guidance]` to `[shim_guidance]` and keep its keys (`text`, `command`, `url`) as they are; written inline, move `shim_guidance = { ... }` out of `[delivery]` to the top of the file, before the first table. The bundled `codex-cli` profile already uses it. See [`profiles/README.md`](profiles/README.md#shim-guidance).
- **A request a Windows `.cmd` / `.bat` program cannot carry is refused before it is approved.** `open_window` with a `model` or `effort` whose template holds a character the command interpreter would act on is now refused as `unsupported` before the approval dialog, instead of failing at spawn after it was approved; a `send_handoff` that opens a window and an `open_task_window` with an instruction are refused the same way as before. The message ends with the profile's `[shim_guidance]`, and the same limits are listed ahead of time in `list_profiles` and the GUI.
- **A launch profile with an unknown top-level or `[command]` key is now left out of the profile list with a warning**, as a profile with an unknown key in any of its other tables already was. Such a key used to be ignored without a word, so a misspelt table heading such as `[hook]` gave a profile whose windows silently had no hooks.
- **A playbook's `[limits]` no longer takes `interrupt_method`.** Its only working value was the default, `bytes`; `signal` was never implemented and made every `interrupt_window` fail with `unsupported_interrupt_method`, an error code that is now gone. A playbook that still sets the key fails to load, like one with any other unknown key, so remove the line.

### Fixed

- A `wait_for_status` or `wait_for_report` that a CLI dropped at the end of its turn without cancelling it (Codex CLI, and Muse Code when its own call time limit runs out) kept waiting in the daemon until its `timeout_sec`, holding one of the bridge's connections, and a report that reached the caller in that time was handed to the dropped call and lost. Both now end with the turn: the wait answers as if its time had run out, and `wait_for_report` takes no report, so it waits in the inbox for the next call.
- A message typed into a window that had no focus -- behind other windows in the MDI, in an app that was in the background, or with an approval dialog open -- could wait until you clicked its input line when the CLI is GitHub Copilot CLI. The daemon now tells the CLI it has the focus while it types, and tells it the view's focus again once the CLI has drawn something after the last keys.
- A window whose profile's `[hooks]` table was dropped at launch -- no settings directory, settings that could not be written, or a Windows `.cmd` / `.bat` file that would reinterpret them -- still took part in chat and handoffs, so a handoff to it waited for a CLI that never runs the hooks until `undelivered_timeout`. Such a window now takes no part, and a handoff to it is answered `undelivered_no_delivery` at once, as for hooks left out because their registration was not in place.
- A Codex CLI window of a named instance could still see the default instance's registered `yagura` server, which Codex CLI starts without the window's variables, so it connected to the default instance's daemon as an outside client and could not say which window it was. When the daemon opens a Codex CLI window it now reads the CLI's registrations and turns off, for that window only, every yagura bridge registration except its own, through the new `[mcp_registration.list]` table of the bundled `codex-cli` and `wsl-codex-cli` profiles. Claude Code has no documented way to do this at launch, so its windows are unchanged.
- A Claude Code or Codex CLI window of a named instance with yagura registered from Settings > Integrations had two yagura MCP servers, and the registered one could not say which window it was, so its calls were not attributed to the window. The bundled profiles now name the injected server the way Register does (`yagura-<instance>`), so the two are one. Their tools are therefore listed under `yagura-<instance>` rather than `yagura` in such a window. A WSL Codex CLI window could not say which window it was in any instance, because Codex does not pass `WSLENV` on to the bridge; `wsl-codex-cli` now sets it.
- A second daemon started for an instance whose daemon was still starting up could exit as a failure and log that a non-daemon process held the endpoint, because it gave the first one 500 ms to answer a ping. It now asks the endpoint's lock instead, which a daemon takes when it binds and the system releases when it dies, so it exits as a success however long the first one takes. On Windows the lock is new, so a daemon of 0.1.0 still running when a newer one is started is now taken for a process that is not a daemon, and the newer one exits as a failure; the app still connects to the running one.
- A chat mention of a window did not reach anyone when two windows had the same name (opening two windows from one profile gave them both the profile's name), and nothing told the sender. Names are now unique, so a mention reaches the window it names, and a mention that matches no one in the room is now named in a notice above the chat input.
- A window opened after the chat panel was already open now appears in the `@` suggestions and the participant count right away, and leaves them when it ends or is renamed; before, it showed up only after someone posted. Choosing a suggestion with the arrow keys no longer snaps back to the first one when the key is released.
- On macOS, a chat mention picked from the `@` suggestions could reach no one: as the message was typed on, macOS turned the closing `"` of `@"Claude Code"` into a curly quote, which ends no mention. The app's text fields no longer have their quotes, dashes and words rewritten as you type, so mentions, commands, paths and names are sent as typed; they no longer show spelling marks either.
- A handoff or chat message to a window that took it without visibly starting work could be written into that window two or three times: a later attempt read the emptied input line as the text having been lost. Once the submit key has been pressed, yagura no longer writes the text again; it only presses the key again over text it still sees in the input line.
- When two texts waited for a window that yagura types into (the bundled Antigravity CLI and GitHub Copilot CLI profiles), the second could be typed before the CLI had started on the first, and so joined the first one's turn (seen with GitHub Copilot CLI). The next text is now typed only once the window has reacted to the previous submit key and is waiting for input again; a window that shows no reaction within its detection definition's `delivery_confirm_ms` is typed into as before. The wire protocol, the MCP tools and the profile format do not change.
- A message or handoff that is being delivered no longer leaves yagura's own half-written text (including the `x` probe) in a window's input line when someone types, `send_keys` or interrupts meanwhile: the delivery takes its text back in front of that input, writes nothing more, and checks the line before it answers. Text typed in front of a waiting notice no longer sets off a loop of probes that kept the notice from arriving. Where the check cannot confirm the text gone, the call still reports that something may remain.
- A `send_message`, a handoff or a chat message could reach a CLI while it was still drawing an approval dialog, so its keys could answer the dialog (an Enter could approve it). yagura now writes into a window only once the CLI has finished drawing its screen -- the cursor is shown again and no synchronized update is open -- and still never writes on an approval dialog. A CLI that keeps the cursor hidden while its input line sits idle receives nothing from yagura.
- A `send_message`, a handoff or a chat message whose text ended in a word starting with `@` (`please review @src`, or a chat message ending in `@user.`) opened the input completion of Codex CLI and Antigravity CLI, and the delivery could stall there with the text and the probe left in the input line. yagura now ends every text it types and submits with one space of its own, so the cursor never rests on the end of the sender's text.
- On macOS 26, the app icon fills the rounded square like other Mac apps instead of sitting small on a gray plate. If the Dock still shows the old icon after you update, remove yagura from the Dock (Options > Remove from Dock) and open it again.
- Registering Antigravity CLI in Settings > Integrations no longer fails with "no path to the daemon can be written" when the daemon's folder has a space in its path: on macOS the daemon copy that CLI hooks run now lives in `~/.local/state/yagura/bin` (or under `$XDG_STATE_HOME`) instead of `~/Library/Application Support`, and on Windows a path with a space is written by its 8.3 short name; where there is none, the registration fails with a message that says so.
- Commands run once and the detached daemon no longer inherit stray file descriptors or handles from the process that starts them, so a one-shot command no longer waits for an unrelated child started at the same moment to exit. On Windows the daemon is now started through the same explicit handle list as other commands, rather than through the standard library's process launcher.

### Security

- `rmcp` is updated to 3.7.0 for [GHSA-5p52-q7pq-9fq2](https://github.com/advisories/GHSA-5p52-q7pq-9fq2). The advisory is in the SDK's OAuth client, which `yagura-mcp` does not build (it enables only the `server`, `macros` and `transport-io` features), so yagura was not exposed.

## [0.1.0] - 2026-10-13

The first public release of yagura: a desktop app that runs any command -- an agent CLI such as
Claude Code, Codex CLI or Antigravity CLI, or a plain shell -- in its own window, watches each
window's status, and lets agents in those windows work with each other through an MCP server.

### Added

#### Windows and layout

- Each window is a pseudo-terminal running any command you choose, drawn in a floating frame you can drag, resize from any edge or corner, minimize, maximize and close.
- Maximizing a window switches to a tab bar: click a tab to switch windows, drag it to reorder, and restore to get every window back where it was.
- The Tile windows button in the sidebar header lays every window out in an even grid; each room heading can also tile, minimize or restore just that room's windows.
- The sidebar lists windows grouped by room (the git repository or directory a window runs in), in a fixed order that does not jump around when a status changes.
- Each row shows the window's name, status, vendor and working directory, with rename, interrupt and close buttons; the interrupt button is shown disabled when interrupting is not allowed.
- A badge counts the windows waiting for you; pressing it jumps to the next one.
- The new-window dialog opens a window from a launch profile, or from a command, working directory, name and detection definition of your own; a Browse button picks the working directory.
- Each window's menu offers a per-window theme and rename.
- Every button that shows only an icon names itself in a tooltip on hover, including the side rail's Windows, Plans, Chat and Settings buttons and every close button.
- A window shows what the daemon's model of its terminal holds -- the same text `read_output` and status detection read -- so the window, its text and its status agree after a resize, with wide characters, on the alternate screen and on the cursor's line. The GUI only draws the cells the daemon sends; box-drawing and block characters are drawn to fit the cell so their lines join.
- The mouse wheel, or `Shift+PageUp` / `Shift+PageDown`, scrolls back through a window's history, unless the program in the window takes the wheel itself. Typing or pasting brings the window back to the bottom.
- Text an input method is still composing is drawn underlined inside the line, at the cursor.
- In a window, `Shift+Enter` inserts a newline in an agent CLI's input, and on Windows `Ctrl+V` pastes.
- Copy and paste follow each platform's terminal convention: `Ctrl+Shift+C` / `Ctrl+Shift+V` on Windows and Linux, `Cmd+C` / `Cmd+V` on macOS. A right-click copies the selection or pastes on Windows, and opens a Copy / Paste menu on macOS and Linux. Copying clears the selection, so the next right-click on Windows pastes. Drag selects, a double-click selects a word and a triple-click a line. When the program in a window captures the mouse, clicks and the right-click go to that program; holding `Shift` brings back yagura's handling.
- Elsewhere in the app, a right-click does not open the web view's own menu, whose Reload item would throw away every open window's view; text fields keep their operating system's cut / copy / paste menu.
- A window's program is told it runs in yagura's terminal (`TERM=xterm-256color`, `COLORTERM=truecolor`), whichever terminal yagura was started from: variables a terminal sets to name itself, such as `TERM_PROGRAM` or `VSCODE_*`, are not passed on, so a CLI does not, for example, turn off right-click paste because it thinks it is inside VS Code. A profile's `[env]` can still set any of them.
- The daemon answers a program's terminal queries itself (device attributes, status and cursor position reports, mode queries), so a program gets its answers even while no GUI shows the window. Color queries are answered with the window's theme colors once the GUI has opened the window.
- Closing or interrupting a window from the GUI asks for confirmation first; closing ends the window's whole process tree.

#### Status detection

- Every window reports one of seven statuses: `running`, `waiting_input`, `waiting_approval`, `interrupted`, `idle`, `exited` and `unknown`, shown in the sidebar, the title bar and the tab bar.
- Status comes from detection definitions (TOML) that read the window's screen. Definitions for `claude-code`, `codex-cli`, `antigravity-cli` and `generic-shell` are built into the daemon; your own go in the `detection` directory under the config root and override a built-in one of the same name. See [`crates/yagura-daemon/detection/README.md`](crates/yagura-daemon/detection/README.md).
- Detection is fail-safe: when a screen cannot be read with confidence, the window is `unknown` rather than guessed, and interrupting, typing text and chat delivery into it are refused. Closing an `unknown` window is always allowed.
- An `unknown` window says why (`no_definition`, `no_rule_matched`, `screen_lost`, `detector_stopped`, `not_yet_judged` or `declared_unknown`), in the GUI and in MCP replies.
- Approval prompts and choice dialogs of the bundled agent CLIs are detected as `waiting_approval`.
- Text being typed in an agent CLI's input line is left out when its status is judged, so a draft that quotes a prompt or a spinner line does not change the status.
- Status is judged only on a screen the CLI has finished drawing, so a repaint split across reads does not make the status flicker; the composer is read the same way before a write.
- Codex CLI shows `running` while its composer holds a draft during a turn, not only while its `Working` line is drawn.
- Antigravity CLI keeps its status while its composer holds a draft with blank lines, including a draft folded under `↑ N more lines`. A definition opts into reading blank lines as part of the body with `blank_lines_in_body` in `[composer]`; declare it only for a CLI whose dialogs hide the cursor.
- Windows opened from the bundled Claude Code, Codex CLI and Antigravity CLI profiles have the CLI report the start and end of each turn through its own hooks (`yagura-daemon --emit-status`, authenticated with a per-window token). A window then shows `running` while a reply streams under an input line that looks idle, and `waiting_approval` when the dialog is too small to read. A screen with a clear status still wins, and a window with no reports is judged by its screen alone. See [`crates/yagura-daemon/detection/README.md`](crates/yagura-daemon/detection/README.md#structured-sources---emit-status).
- Codex CLI and Antigravity CLI report once yagura is registered with them in Settings > Integrations, which also writes the hook settings they need (Codex CLI's hook trust in `~/.codex/config.toml`, a `yagura` entry in `~/.gemini/config/hooks.json`) and takes them out again on Remove.
- A report stands until the next one; `--emit-status` takes only a status and `--source`, with no time-to-live. A turn with no output for 5 seconds is taken as over, which covers the interrupts and denied permissions Claude Code sends no hook for. A turn with no report for 2 minutes is taken as over as well, so a screen that keeps redrawing itself cannot hold it open.
- A window whose CLI was given hooks but has sent no report 10 seconds after its screen shows a running turn gets a yellow mark beside its plug icon, and the daemon logs one warning -- the sign that a CLI update changed its hooks.
- `--emit-status` does nothing and exits successfully outside a yagura window, so a hook a CLI runs in every session stays quiet in sessions yagura did not open.
- A `status_event` must name its window: one without `window_id` is refused as `invalid_argument`.

#### MCP server and tools

- `yagura-mcp` is a stdio MCP server that lets an agent control yagura. Its tools are:
  - Windows: `list_windows`, `get_window_status`, `open_window`, `close_window`, `interrupt_window`, `wait_for_status`, `read_output`
  - Input: `send_message`, `send_keys`
  - Setup: `list_detections`, `list_profiles`
  - Handoff and chat: `send_handoff`, `send_chat`, `broadcast_chat`, `read_chat`
  - Plans: `create_plan`, `update_plan`, `get_plan`, `list_plans`, `delete_plan`, `list_roles`, `open_task_window`
  - Reports: `send_report`, `wait_for_report`
- `read_output` and the status summary return a window's text as the window shows it: a line longer than the window comes back whole, a line redrawn in place reads as its last state, and while a full-screen CLI is running only its current screen is returned.
- `send_message` sends a single line of text; `send_keys` sends up to 16 named keys (`escape`, `backspace`, `ctrl_u`, `enter`, `up`, `down`). The arrow keys follow the program's cursor key mode, as a key pressed in the window does.
- The daemon never types text into a window whose definition has no input line (such as a plain shell); `send_message` and `send_handoff` to it are refused as `no_composer`. A definition that has an input line but no `probe` in `[input]` gets no line of the daemon's own either: a one-line `send_message`, a `send_handoff` and a task instruction are refused there as `no_composer`, and no notice or chat message is typed there, while `send_message` text without a newline is still typed. The definition still loads and the window's status is still detected; adding a `probe` is all it needs.
- `yagura-mcp` runs up to four tool calls at once, each over a connection of its own to the daemon, so a call waiting on a stalled window, an approval or `wait_for_status` does not hold up the agent's other calls; a call beyond that waits for one to finish.
- Cancelling a tool call from the MCP client (`notifications/cancelled`) ends it at once: `yagura-mcp` answers with an error and drops that call's connection to the daemon, which the daemon treats as the requester leaving -- a pending approval is withdrawn, and a message that has not shown yet is never submitted and is taken back where the definition has a `clear` key. A requester that disconnects is treated the same way.
- A CLI that drops a tool call still out when it ends its turn, without cancelling it, is caught by its window instead: when the requester's detection definition sets `[requests] abandoned_at_turn_end` (the bundled Codex CLI definition does), its `send_message` or `send_handoff` is answered `not_written` at once when its window, having been `running`, comes to rest at `waiting_input`, `interrupted`, `idle` or `exited`, and the text is taken back as for a cancelled call.
- A `send_message` waiting for its text to show does not hold up the daemon's other replies on the same connection; it counts toward that connection's limit on pending waits, as `wait_for_status` does.
- `send_keys` is written at once, even into a window where a message is waiting to show, so it can dismiss a dialog that holds a delivery up; the waiting delivery then stops, as it does when you type into the window.
- Before writing, the daemon checks the window's screen, so it never presses Enter into an approval prompt or on top of text someone else is typing.
- Windows yagura opens from the bundled Claude Code and Codex CLI profiles can use the tools without any MCP registration in the CLI; a plug icon shows which windows are connected.
- For sessions yagura did not start, Settings > Integrations registers or removes the bridge with each CLI through the CLI's own `mcp add` / `mcp remove`. See [`docs/mcp-setup.md`](docs/mcp-setup.md).

#### Approvals

- Destructive tools (`close_window`, `interrupt_window`, `send_message`, `send_keys`, `send_handoff`, `send_chat`, `broadcast_chat`) called by another window or an external client wait for your decision in an approval dialog. A window acting on itself, and the GUI itself, are not gated.
- Starting a window is gated too (`open_window`): an agent that asks to open a window -- with `open_window`, with `send_handoff` from a profile, or with `open_task_window` -- can run any command as you, outside its own CLI's permission prompts. The approval dialog shows the command (or profile) and its working directory. The shipped default lets agents start windows without asking; switch **Open a window** off in Settings > Approvals to be asked each time. A request that could not open anyway (an empty command, a missing directory, the window limit) is refused before anyone is asked, the command is shown with each argument quoted where its boundaries would be unclear, and a request waiting for your decision is withdrawn when the agent drops the call.
- The approval policy comes from `playbook.toml`, which the GUI places in the config root on first run and never overwrites. The shipped default auto-approves only `send_chat` and `open_window`.
- A chat post from a connection that has not identified as a window follows the same switch as any other: it waits for your decision unless `send_chat` / `broadcast_chat` is auto-approved.
- Settings > Approvals turns each tool's auto-approval, and the plan review requirement, on or off without restarting the daemon.
- A request nobody decides on within 60 seconds (configurable) is refused.
- If the playbook cannot be loaded, every gated request is refused and chat is turned off.

#### Handoff, chat rooms and reports

- `send_handoff` passes a reference and a note to another window, either an existing one or a new one opened from a launch profile, and reports whether the receiver reacted (`confirmed`, `unconfirmed`, `not_observed` or `not_written`). The receiver can reply with the same tool.
- Whether a message has shown in the receiver's input line is decided by the order the CLI handles its input, never by a timer: yagura types a harmless character (a detection definition's `probe` in `[input]`, `x` in the bundled ones) behind the message, and presses Enter only once the message shows with that character behind it and the character has been erased again (with `erase`, DEL by default). A slow or heavily loaded machine therefore never has a handoff, chat message, notice or `send_message` given up on because it took long to show, and a long envelope that wraps over several lines is checked the same way. A CLI that dropped the message -- the character shows alone -- gets `not_written`, with nothing left behind. `[` cannot be a `probe`, since every line yagura writes on its own starts with it; the detection README explains how to check a character for a new CLI.
- A CLI that stops handling its input -- at a dialog its definition does not know, for instance -- keeps a delivery into it waiting instead of having it abandoned on a timer. Typing into the window, `send_keys`, `interrupt_window`, `close_window` or cancelling the tool call ends the wait. See [`docs/mcp-setup.md`](docs/mcp-setup.md#send_handoff).
- A message whose requester leaves before it shows is not submitted but taken back, and the take-back is confirmed by the same character: it counts as done only once the character shows alone and is erased again. A busy or stalled CLI therefore never has its text reported gone before it has handled it. When the take-back cannot be confirmed, the sender is told the text may remain, and it is never written a second time.
- A window that has stopped handling its input holds at most one share of the daemon-wide chat delivery budget and one daemon-wide handoff slot, however many deliveries queue for it, and at most 8 deliveries may wait for one window's turn; one past that is refused (`resource_exhausted` for a handoff, `undelivered_exhausted` in chat) without affecting deliveries into other windows.
- `reflect_wait_ms` in a definition's `[input]` has no effect; a definition that sets it still loads.
- How long a delivery waits, how a cancelled call ends and how many calls `yagura-mcp` runs at once change no MCP tool name, argument name or IPC wire format.
- A message never gets mixed into something you are typing: before writing into an input line that looks empty, yagura types the same probe character and writes only once it shows alone, so a draft you just typed or pasted that the CLI has not drawn yet is left alone instead of being sent along with the message. A re-send over its own earlier text does the same when anyone else has typed into the window since. A write still waiting to show stops as soon as someone else types into the same window.
- Moving the focus between windows, or the mouse over a window, does not interrupt a delivery into it, even when its CLI asked for focus or mouse reports.
- The click that selects a window is not passed to a CLI tracking the mouse; the next click is. A click in the window you are already in reaches the CLI, and a delivery waiting there stops as it does when you type.
- A delivery that replaces its own earlier, unsubmitted text with a different body takes that text back even when the CLI draws it folded (for example as a `[Pasted text]` placeholder), as long as nothing else has been written into the window since; the take-back is confirmed by the probe as usual.
- Chat rooms let agents and you post to each other with `@name`, `@"a name with spaces"`, `@parent` and `@user` mentions. Each workspace has its own room, and `main` reaches every window.
- A chat post must carry at least one visible character: a body of only spaces, line breaks or zero-width joiners is refused as `invalid_argument`, and the error tells the agent that not posting is how to send no reply.
- A room halts on loops, monologues or too many turns since your last post, and asks for you; only your post resumes it.
- The Chat panel shows the room list, participants, per-recipient delivery state and a halt banner, and has `@` completion and a post-to-everyone button. The rail's Chat button shows a badge when a room needs you.
- A window can report how its work ended (`send_report`) to the window that opened it; the parent reads reports with `wait_for_report` and gets a one-line notice when reports are waiting.

#### Plans

- A window can hand yagura a plan of tasks with dependencies and write targets. yagura derives the waves, rejects cycles and tasks that could write the same path at the same time, and opens each task's window with the profile, model and effort assigned to it. See [`docs/plans.md`](docs/plans.md).
- Assignments come from your override, the plan's own proposal, or `roles.toml` (with an optional `default_role`), in that order.
- A task can carry a multi-line instruction; its window gets a one-line notice and reads the instruction with `get_plan`.
- A new plan waits for your approval before any of its tasks can open, unless `[plans] require_approval = false`; later changes to an approved plan are marked as new or changed for you to review.
- The Plans panel has a Board tab (waves, assignments, task windows, reports, approve, reassign, hand over or delete a plan) and a Roles tab.
- Plans are kept across daemon restarts.

#### Launch profiles and models

- Launch profiles (one TOML file each) save a command per OS, detection definition, working directory and environment. Profiles for Claude Code, Codex CLI, Antigravity CLI, their WSL versions and a plain shell ship with yagura; a file in the config root's `profiles` holds only what you change, so a new version's defaults still reach you. See [`profiles/README.md`](profiles/README.md).
- A profile whose command does not exist for the current OS is not listed; the WSL profiles appear only on Windows.
- A profile can map `model` and `effort` aliases (such as `fast`, `default`, `strong`) to CLI arguments, chosen in the new-window dialog or through MCP.
- The Plans panel's Models tab edits each alias, offering the models the CLI itself lists, and can put a shipped value back.
- Settings > Profiles shows every value a profile uses, marked Shipped or Changed, and edits the command for the current OS one argument per field, with a reset to the shipped command.
- Settings > Profiles turns a profile off; a disabled profile is hidden and refused as `profile_disabled`.
- On Windows, npm `.cmd` / `.bat` shims are run through `cmd.exe` for you.
- On macOS and Linux, a daemon started outside a terminal gives windows the login shell's environment and a UTF-8 locale, so CLIs installed through Homebrew, nvm or `~/.local/bin` are found.
- No bundled profile turns on a CLI's flag for skipping its own approval prompts.

#### Themes and settings

- Dark (default), Light and System themes, plus your own in `themes.toml` (35 color keys per theme). The rail's theme control shows the current theme as an icon. See [`docs/themes.md`](docs/themes.md).
- A theme can be set per window or per vendor; changes apply at once, including open terminals.
- The Settings, Plans and Chat panels can be resized and reopen at their last size; the Chat panel's room list can be widened.

#### Keyboard

- Twelve operations have shortcuts: next and previous window, next window needing you, new window, close, interrupt, minimize, maximize or restore, moving between the sidebar and a window, and the Chat, Plans and Settings panels. Windows and Linux use `Ctrl+Shift+` keys; macOS uses `Cmd`.
- Settings > Keyboard changes, resets or removes a key, saved to `keymap.toml`. Keys that would take input away from the programs in your windows, or that the system owns, are refused with a reason. See [`docs/keymap.md`](docs/keymap.md).
- `Esc` closes the Chat, Plans or Settings panel, and focus returns to where you were.
- Keys that would reload the GUI are turned off, and on Windows the web view's browser keys (print, find, zoom) are turned off.
- A key an input method is still using is never taken as a shortcut.

#### Sessions and the daemon

- The daemon keeps windows running in the background and outlives the GUI: closing the GUI leaves it running. After upgrading yagura, stop it with `yagura-daemon --shutdown` so the new version starts; restarting the daemon closes every window.
- The daemon starts with no window open: every window is one you, a restored session or an agent opens.
- A window opened without a working directory starts in your home directory on every platform, however the daemon was started. If the home directory cannot be found, it starts in the daemon's own directory and the daemon logs a warning.
- On the next start, the GUI offers to restore the windows of your last session with their layout; windows opened from a profile are reopened from that profile.
- If the daemon disappears while you have windows open, the GUI starts it again (with backoff) and offers a Reconnect button when it gives up. The windows that were running are lost with the old daemon. See [`docs/client-config.md`](docs/client-config.md).
- `YAGURA_INSTANCE` runs a second, fully separate instance (for example a development build) beside your everyday one. Any identifier the rule accepts, up to 16 bytes, works on every platform, including macOS with its long temporary directory. See [`docs/instances.md`](docs/instances.md).
- A window the GUI reconnects to comes back whole from the daemon's model of its terminal: its history and screen with colors, wide characters, the alternate screen and the cursor. The GUI names the size it draws at when it attaches, and again when it reconnects, so the window and the view agree on it after the daemon was started anew.
- A GUI does not show windows from a daemon older than itself: it says so in a banner and asks you to restart the daemon with `yagura-daemon --shutdown`.
- When the daemon cannot open windows because the console host bundled with yagura is missing or damaged, it keeps running and the GUI says why in a banner. Daemon clients can ask for the same list with the `get_daemon_health` request.

#### Platforms and installers

- Windows 11, macOS and Linux. Windows 10 is not supported.
- On Windows, every window runs under the ConPTY that ships with yagura (`conpty.dll` and `OpenConsole.exe` from Microsoft's `Microsoft.Windows.Console.ConPTY` 1.25.260930003, MIT) rather than the one built into Windows, so a resize follows the same rule as on macOS and Linux. If those files are missing or altered, no window opens and a banner asks you to reinstall.
- Windows: a per-user NSIS installer (no administrator rights) that bundles `yagura-daemon`, `yagura-mcp` and the ConPTY above, and installs WebView2 when missing (needs network access). It is not code-signed, so SmartScreen warns on first run. The program goes in `%LOCALAPPDATA%\yagura` and your settings, session store and logs in `%LOCALAPPDATA%\io.github.satoh-y-0323.yagura`, which the uninstaller removes when you choose to delete the app's data.
- macOS (Apple silicon): a `.dmg` whose app, `yagura-daemon` and `yagura-mcp` carry an ad-hoc signature. It is not notarized, so the first launch needs **Open Anyway** in **System Settings > Privacy & Security**.
- Linux: a `.deb` for Debian and Ubuntu that installs the GUI, `yagura-daemon` and `yagura-mcp` into `/usr/bin`.
- Other systems and Intel Macs: build from source.
- WSL: the WSL profiles run a CLI inside your default distribution through `bash`. See [`docs/wsl.md`](docs/wsl.md).

### Security

- The daemon's endpoint accepts connections only from the same OS user. Only the GUI executable the daemon was started with can become the approver.
- The GUI, `yagura-mcp` and the daemon's own commands (such as `--shutdown`) connect only to a daemon running as the same OS user, so on a shared machine another user cannot stand in for yours by taking its endpoint name first.
- Any MCP client connected to yagura can read the recent output of every window. Do not run terminals that show secrets as yagura windows.
- Handoff envelopes, chat messages and reports are delivered as data from another agent; a receiving agent should treat them as untrusted input, not instructions.
- The session database stores each window's command line and working directory, chat messages, plans and their reports without encrypting them. Do not put secrets in a window's command line.
- Pasted text cannot end a program's bracketed paste early: yagura removes the paste markers from it before writing.
- A window's status is advisory: another process of the same user can forge it, so do not base security decisions on it alone.
